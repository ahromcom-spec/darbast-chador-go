# Architecture Decisions
- Aggregate executive marker waiting categories through `executionMarkerStatuses`; collapsed location groups use all their orders, while expanded markers use only their own orders so mixed statuses remain visible.
- Resolve statement employer display from each order's invoice override through `statementEmployer`; retain multiple employers explicitly and never change customer ownership or financial allocation for a display override.
- Prepare new order videos with `prepareOrderVideo` before upload, fingerprinting and metadata creation; serialized FFmpeg workers keep memory bounded and failures never upload unprocessed originals.
- Use `openPrintWindow` for order and statement printing: run native print in the disposable tab, release the preview dialog on print start, and close/focus back on print completion so app interaction is not stranded.
- Share compact date markup and column-layout CSS through `statementPrintLayout` across statement preview, print and PDF to keep presentation consistent without changing billing.

- Read each order's statement cost only through `orderStatementCost` (total_price, else payment_amount unless billing-only/discounted); a DB trigger fills a zero total_price from payment_amount so legacy-priced orders never vanish from statements.
- Compute statement financial summaries with `statementTotals` using uncapped receipts; refresh through scoped RLS realtime subscriptions plus visible-page reconciliation so cost changes retain credit and never truncate payments.

- Detect «اجرای داربست بدون اجناس» only through `isScaffoldingNoMaterials`; this keeps invoice and workflow branching consistent across legacy and current orders.
- Renewal/repair operational ownership stays in `order_id`; financial ownership uses `COALESCE(billing_order_id, order_id)` through `orderChargeBilling`, so separation never breaks dates, media or part links.
- Create charge-separated orders only through the manager-authorized atomic `transfer_order_charges` RPC; expose full order and collection UI, keep zero base price and suppress duplicate initial-installation automation. Synchronize their rental period from financially owned approved renewals.
- Resolve invoice customer identity through the order-scoped `get_order_customer_identity` RPC with snapshot fallbacks; restricted profile access must not erase inherited identity or expose unrelated customers.
- Read customer and manager daily activity through `get_order_report_activity`: canonical report rows preserve all modules and edits; legacy logs are fallback only, with server-side order access checks and no personnel/global notes.
- Delete empty closed statements only through the manager-authorized `delete_empty_closed_statement` RPC; count all linked orders and retain statements with cheque or payment-submission history to protect financial records.- Upload order media only through `uploadToStorageWithProgress` (resumable over 8MB, refreshed auth via onBeforeRequest, normalized video content type) so large videos never fail on single-request limits.
- Search HR staff through `matchesHRSearch`, derive edit status through `resolveHRStatus`, and identify staff in reports/salary only through `hrStaffCode`; the phone is the identifier when present, otherwise a DB-issued unique personnel code; a DB trigger moves report rows and salary settings when the identifier switches so history keeps matching.
- Delete customer addresses only through `deleteCustomerLocation`: it removes the address's non-archived awaiting-approval orders and empty projects first and refuses when any other order exists, because address lists intentionally show any address that still has orders.
- Keep one `sms_logs` row per SMS: automatic retries and manual resends of a failed message carry `logId` and update that failed row (`canReuseSmsLog`), and queued retries reuse their `scheduled_sms` row via `scheduledId`, so customer message history never fills with duplicate failures.
- Resolve manager-defined SMS elements only through `_shared/smsCustomVariables` (source catalog, formatting, fallback) in both `send-order-sms` and the SMS management preview; "latest payment" means latest registered while its date is the chosen deposit date, and disabled elements emit fallback text so raw tokens never reach customers.
- Preview queued SMS text only through `send-order-sms` with `previewScheduledIds`: it reuses the real message builder in preview mode (no send, log, delay or Bale) and reads queue rows with the caller's RLS, so the waiting tab shows exactly what will be sent.
